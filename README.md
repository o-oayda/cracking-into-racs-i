# cracking-into-racs-i

## Installation
### Requirements
- `uv` project manager, see [here](https://docs.astral.sh/uv/)
- Python 3.12
- Unix-like system; Windows is untested

### Virtual environment
Run `uv sync --locked` to create a virtual environment and install the base
dependencies. Alternatively, if you have a NVIDIA GPU, run with the flag `uv
sync --locked --extra cuda` for the optional cuda backend, which is useful for
efficiently generating simulations for the posterior predictive residuals plot
via JAX. This has been tested to work fine on a RTX 5070 Ti, H100 and L40 GPU.
Otherwise, the numpy backend will be used; this will get the job done as long
as the job is distributed across many threads (see below) but will take quite a
bit longer on the `posterior_predictive_residuals` rule.

Products 1 and 3 are needed to deduce the functional dependence
between flux and temperature, while Product 4 is needed for the flux
uncertainty lookup. Product 2 is needed for creating Figure 2 in the
paper, as NVSS is used to derive the flux ratio. Lastly, Product 5
contains the posterior samples and marginal likelihoods needed to reproduce the
key results from the paper.

To obtain the data, first download Products 1, 3 and 4 from the CSIRO Data Access
Portal (DAP) listing for the paper, and Products 2
and 5 from the [releases](https://github.com/o-oayda/cracking-into-racs-i/releases).

## Reproducing the paper
### Verifying and preparing data

Run `uv run snakemake verify_data --cores 1` to verify the files listed in
`required-data.yaml` in the directories above. This will check the files
against the hashes in `required-data.yaml` to ensure the integrity of the data.

The mid1 catalogue is provided with units of Jy for the source total flux and
total flux error, but the libraries expect catalogues with units of mJy.
Thus, before verification, the `prepare_mid1` rule checks the original mid1 catalogue
SHA256 hash,
calls astropy's `convert_unit_to(u.mJy)` on
`Total_flux` and `E_Total_flux`, and overwrites the same FITS file.
The converted catalogue must then match `modified_sha256` in `required-data.yaml`.
Subsequent calls of this rule will skip if the new catalogue matches the modified
hash.

### Regenerating plots
This section describes how to reproduce all plots in the paper from the raw
data products and the inference artefacts. If you want to recreate the
artefacts themselves, i.e. run the full SBI pipeline/NLE, see the next
section.

For a very slow workflow, run
```bash
uv run snakemake all --cores 1
```
This isn't really recommended since it will be quite slow when generating
simulations from posterior draws.

Instead, if you have the cuda deps setup and an NVIDIA GPU, be sure to pass
this flag to snakemake to take advantage of jax GPU-accelerated simulations:
```bash
uv run snakemake all \
    --config posterior_predictive_backend=jax-cuda \
    posterior_predictive_batch_size=5 \
    --cores 1
```
In this case, the `cores` argument does not really matter, so just leave it at
1.

Otherwise, the `numpy` backend with `catsim`'s `batch_simulate` will be used.
In this case, you can specify a number of threads to use like so, being sure
to match the numbers in the `set-threads` and snakemake `cores` arguments (this
argument now matters):
```bash
uv run snakemake all \
    --config posterior_predictive_backend=numpy \
    --set-threads posterior_predictive_residuals=N \
    --cores N
```
Change `N` with however many threads are available on your system. This will
speed up the production of the simulation for the residuals plot by
distributing the jobs over many workers via `joblib`.

### Regenerating artefacts
This will take substantially longer. On an H100 GPU, from testing expect about
3.5 hrs per model.

First, clone the `dipolesbi` library @ [0.1.5-fix2](https://github.com/o-oayda/sbi/tree/v0.1.5-fix2) into a separate directory somewhere on your system. Note that this
initial part is independent of the `cracking-into-racs-i` repo. Instructions
on setting up the `dipolesbi` virtual enviroment are provided in that repo's
`README`.

Once done, you should be able to run the Snakemake workflow from the `dipolesbi`
repo root via:
```bash
uv run --locked snakemake \
    --snakefile workflow/Snakefile all \
    --configfile workflow/configs/sites/example-site.yaml \
    --config experiment=$EXPERIMENT_NAME \
    --cores 1

uv run python dipolesbi/scripts/copy_analysis_artifact.py \
    $EXPERIMENT_NAME \
    /path/to/cracking-into-racs-i
```

Note a couple of things from the above commands:

- The `$EXPERIMENT_NAME` env var sets the name of the model to run.
A model just means one that appears in Tables
2 and 3 in the paper. To find the appropriate model string to pass as the
argument, consult the table below. You could choose to iterate through all of
these in a bash script if you wish to regenerate all artefacts.
- A path to `example-site.yaml` is set for the `config` arg. This is important
for specifying where data products are located on the system that the inference
is being run on. For more details, see the README in `dipolesbi`.
- The analysis artefacts should be copied into the directory where you cloned
`cracking-into-racs-i`, which is achieved by the `copy_analysis_artifact.py`
script as shown in the last command above.

| Model | String |
| ---   | ---    |
| Fiducial: Free dipole; temperature response; clustering | "{SAMPLE}_fiducial" |
| Free dipole; no temperature response; clustering  | "{SAMPLE}_notemp" |
| CMB direction; temperature response; clustering   | "{SAMPLE}_cmbdir" |
| CMB dipole; temperature response; clustering    | "{SAMPLE}_cmbdip" |
| Free dipole; temperature response; no clustering    | "{SAMPLE}_noclus" |

SAMPLE here refers to either "racs_low3" or "racs_mid1". So, for example, the
fiducial model for RACS-low3 is specified by "racs_low3_fiducial".

While running, per-round results will appear in subdirs in `results` labelled
by the model being run. When the last round is completed, the final
chains as well as other provenance files will be copied into
`cracking-into-racs-i`, again labelled by model.

Once copied, inside the `cracking-into-racs-i` repo, run
```bash
python scripts/update-analysis-artifact.py artifacts/cache
```
Note that this will update each artefact's `sha256` in
`workflow/config/artifacts.yaml`. Essentially, since the
reproduced results will inevitably have small differences from the packaged
artefacts, the hashes will be different. This is expected behaviour.

With the hashes updated, you can follow the steps in the section above to
generate plots, which may have very minor differences from those appearing in
the paper.
